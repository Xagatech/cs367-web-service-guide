Web คืออะไร และทำงานยังไง?

Web คือระบบส่งข้อมูลผ่าน Internet โดยใช้โปรโตคอล HTTP (HyperText Transfer Protocol) เป็นภาษากลาง ทุกครั้งที่เปิดเว็บไซต์ browser จะส่ง request ไปหา server แล้วรับ response กลับมาแสดงผล

เปรียบเทียบ: Web เหมือนระบบสั่งอาหาร — ลูกค้า (browser) เปิดเมนู (เว็บไซต์) แล้วสั่ง (request) ครัว (server) ทำแล้วส่งมา (response) ลูกค้าได้กิน (แสดงผล)

Website vs Web Application

Website (Static)

แสดงข้อมูลอย่างเดียว ไม่มี logic ไม่มี interaction ทุกคนเห็นข้อมูลเดิม เช่น หน้าประวัติบริษัท, blog บทความ

เปรียบกับ: ป้ายโฆษณา — ดูได้อย่างเดียว

Web Application (Dynamic)

มี business logic, มี state, ข้อมูลเปลี่ยนตามผู้ใช้ เช่น Gmail, Facebook, ระบบจองตั๋ว

เปรียบกับ: พนักงาน ATM — รับคำสั่ง ประมวลผล คืนผลลัพธ์

รูปแบบพื้นฐานของ web — มีสองฝั่งเสมอ:

  • Client — ฝั่งที่ร้องขอข้อมูล (browser, mobile app, หรือ app อื่น)
  • Server — ฝั่งที่ประมวลผลและตอบกลับ
สำคัญมาก — Stateless: Server ไม่จำ client ระหว่าง requests เหมือนพนักงานร้านสะดวกซื้อที่จำลูกค้าแต่ละคนไม่ได้ ดังนั้น ทุก request ต้องพกข้อมูลที่จำเป็นไปครบ (เช่น token แสดงว่าเป็นใคร) ไม่งั้น server ไม่รู้ว่าคุยกับใคร

API คืออะไร?

API (Application Programming Interface) = สัญญาระหว่าง 2 ระบบ ว่าจะคุยกันยังไง กำหนดว่าต้องส่งอะไรมา แล้วจะได้อะไรกลับไป

เปรียบกับเมนูอาหาร: เมนูบอกว่า "สั่ง ข้าวผัด แล้วจะได้ข้าวผัด" นั่นคือ API เมนูไม่ได้บอกวิธีทำ แค่บอก input/output — API ก็เช่นกัน บอกว่า "ส่ง student_id มา จะได้ข้อมูลนักศึกษากลับไป" โดยไม่สนว่า server ทำยังไง

Service Architecture: Decomposition & Composition

Decomposition (แตกย่อย)

แบ่ง application ใหญ่ (Monolith) ออกเป็น services เล็กๆ แต่ละ service ทำแค่ 1 หน้าที่ ง่ายต่อการดูแล scale ได้เฉพาะส่วนที่ต้องการ

Monolith → User Service + Order Service + Payment Service

Composition (รวมกัน)

นำ services หลายตัวมาทำงานร่วมกัน มี 2 แบบ:

  • Orchestration — มี coordinator กลางสั่ง
  • Choreography — แต่ละ service ตัดสินใจเองผ่าน events

ปัญหาก่อน REST — ทำไมถึงต้องมี?

ลองนึกภาพว่าก่อนมี REST นักพัฒนาแต่ละคนออกแบบ API ตามใจ — บางคนใช้ GET /getUser บางคนใช้ POST /fetchUser บางคนใช้ POST /user/retrieve ไม่มีมาตรฐาน ทำให้ทีมอื่น หรือ developer ใหม่ต้องไปอ่าน documentation ทุกครั้ง

Roy Fielding แก้ปัญหานี้ในปี 2000: เขาเสนอ REST เป็น architectural style ในวิทยานิพนธ์ปริญญาเอก — กำหนด "กฎกลาง" ว่า API ควรออกแบบยังไง ให้ทุกคนเข้าใจได้โดยไม่ต้องอ่าน doc ทั้งหมด

ROA — Resource-Oriented Architecture

ROA คือแนวทางออกแบบ API โดยยึด resource (สิ่งของ/ข้อมูล) เป็นศูนย์กลาง มี 4 คุณสมบัติที่ต้องมี:

1. Addressability — ทุก resource ต้องมี URI

ทุกสิ่งที่เราต้องการเข้าถึงต้องมีที่อยู่ (URI) เฉพาะของตัวเอง เหมือนทุกบ้านต้องมีที่อยู่ถึงจะส่งจดหมายได้

/students              → นักศึกษาทั้งหมด
/students/12345        → นักศึกษา id 12345 คนเดียว
/students/12345/grades → เกรดของนักศึกษา 12345
/courses/CS367         → วิชา CS367
/courses/CS367/students → นักศึกษาที่ลงทะเบียน CS367
ทำไมต้องมี URI เฉพาะ? ถ้าทุกอย่างใช้ URL เดียวกัน เช่น POST /api แล้วแยกด้วย body เราไม่รู้ว่า resource นั้นอยู่ที่ไหน ไม่สามารถ bookmark, cache, หรือ link ได้
2. Statelessness — Server ไม่จำ state ของ client

ทุก request ต้องพกข้อมูลที่จำเป็นมาครบ server ไม่เก็บ session ว่า "ตอนนี้ client ทำอะไรอยู่"

เปรียบกับ: call center ที่มีพนักงานหลายคน ถ้าโทรครั้งแรกคุยกับพนักงาน A แล้วโทรครั้งที่สองเจอพนักงาน B — B ไม่รู้ว่าคุณคุยอะไรกับ A ไปแล้ว ดังนั้นคุณต้องบอกข้อมูลซ้ำใหม่ทุกครั้ง (เช่น ชื่อ, เลขที่สั่งซื้อ)
ทำไมดี? ถ้า server ไม่เก็บ state เราสามารถเพิ่ม server ได้กี่ตัวก็ได้ เพราะ request ใดๆ ไปหา server ตัวไหนก็ได้ผลเหมือนกัน — นี่คือพื้นฐานของ horizontal scaling
ข้อสอบมักหลอก: Stateless ไม่ได้หมายความว่าไม่มี state — client ยังมี state ได้ (เช่น cart, login status) แค่ server ไม่เก็บแทน client เท่านั้น
3. Connectedness (HATEOAS) — Response มี links นำทาง

Hypermedia As The Engine Of Application State — response ควรมี links บอกว่าทำอะไรได้ต่อ เหมือน web page มี hyperlinks

{
  "id": 12345,
  "name": "Alice",
  "_links": {
    "self": "/students/12345",
    "courses": "/students/12345/courses",
    "grades": "/students/12345/grades",
    "update": "/students/12345"
  }
}
ประโยชน์: Client ไม่ต้อง hardcode URLs — ตาม links ใน response ได้เลย ถ้า server เปลี่ยน URL structure ก็แค่เปลี่ยน links ใน response
4. Uniform Interface — ใช้ HTTP methods ตรงตามความหมาย

ต้องใช้ HTTP methods ตามความหมายมาตรฐาน ไม่คิดเอง ทุกคนที่รู้จัก REST จะเข้าใจ API ได้ทันที

ต้องการทำอะไร✓ Uniform Interface✗ ไม่ใช่
ดูนักศึกษาGET /students/1POST /getStudent
สร้างนักศึกษาPOST /studentsGET /students/create
ลบนักศึกษาDELETE /students/1POST /students/1/delete

Request Parameters — ส่งข้อมูลไปหา Server ยังไง?

มี 3 ทางหลักในการส่งข้อมูลไปกับ request แต่ละทางใช้กรณีต่างกัน:

ชนิดตำแหน่งใช้สำหรับตัวอย่าง
Path Parameterใน URL pathระบุ specific resource (บังคับ)GET /students/12345
Query Parameterหลัง ? ใน URLกรอง, เรียง, paginate (optional)GET /students?year=3&sort=name
Request BodyBody ของ requestส่งข้อมูลจำนวนมาก (POST/PUT/PATCH)POST /students → JSON body
ทำไมไม่ส่งทุกอย่างทาง body? GET request ไม่มี body ตามมาตรฐาน HTTP — และ URL ทำให้ bookmark/cache/share ได้ ดังนั้น filter ต่างๆ ควรอยู่ใน query string

JSON — JavaScript Object Notation

Format มาตรฐานของการส่งข้อมูลใน REST API ปัจจุบัน — มนุษย์อ่านได้ เครื่องอ่านได้ กระชับ

{
  "name": "Alice",          // String — ต้องมี double quotes เสมอ
  "studentId": 12345,       // Number — ไม่มี quotes, รองรับทศนิยม
  "gpa": 3.75,              // Number (float)
  "isActive": true,         // Boolean — true หรือ false (lowercase เท่านั้น!)
  "advisor": null,          // Null — ไม่มีค่า
  "courses": [              // Array — รายการ
    "CS367",
    "CS101",
    "MATH201"
  ],
  "address": {              // Object — nested key-value pairs
    "city": "Bangkok",
    "district": "Pathumthani",
    "zip": "12120"
  }
}
ข้อผิดพลาดที่พบบ่อย: JSON ใช้ double quotes เท่านั้น (ไม่ใช่ single quotes), ตัวสุดท้ายใน object/array ไม่มี trailing comma, Boolean ต้องเป็น true/false (lowercase) ไม่ใช่ True/False

XML — eXtensible Markup Language

Format เก่ากว่า JSON ใช้ tag เหมือน HTML ยังพบมากใน Enterprise systems และ SOAP APIs

<?xml version="1.0" encoding="UTF-8"?>  <!-- Declaration บังคับอยู่บรรทัดแรก -->
<student id="12345">                     <!-- Root element + attribute -->
  <name>Alice</name>                     <!-- Child element -->
  <gpa>3.75</gpa>                        <!-- ทุกอย่างเป็น string ใน XML! -->
  <courses>                              <!-- Nested elements -->
    <course code="CS367">Web Services</course>
    <course code="CS101">Intro to CS</course>
  </courses>
</student>

Authentication vs Authorization — สองสิ่งที่ต่างกันมาก

เปรียบกับเข้าออฟฟิศ: ตอนเข้าประตู รปภ. ดูบัตร = Authentication (คุณคือใคร?) เมื่อเข้าแล้ว จะเข้าห้อง CEO ไม่ได้เพราะไม่มีสิทธิ์ = Authorization (คุณทำอะไรได้บ้าง?)

Authentication (AuthN) — ยืนยันตัวตน

ตอบคำถาม "คุณคือใคร?" — ต้องผ่านก่อน authorization เสมอ

  • Username + Password
  • JWT Token
  • Biometric (fingerprint, face)
  • OAuth (ล็อกอินผ่าน Google)

Authorization (AuthZ) — ตรวจสิทธิ์

ตอบคำถาม "คุณทำอะไรได้บ้าง?" — ทำหลัง authn เสมอ

  • RBAC — ตาม role
  • ABAC — ตาม attributes
  • ReBAC — ตาม relationships
  • ACL — รายชื่อสิทธิ์เฉพาะราย

MFA — Multi-Factor Authentication

การยืนยันตัวตนหลายชั้น — ต้องผ่านหลายปัจจัย ทำให้ปลอดภัยกว่า password อย่างเดียว

Factorคืออะไรตัวอย่างข้อเสีย
Something you KNOWสิ่งที่รู้Password, PIN, security questionถูกขโมยได้ถ้า leak
Something you HAVEสิ่งที่มีOTP จาก app, SMS, hardware keyอาจทำหาย

Resilience Patterns — ทำให้ระบบทนทาน

Timeout — ไม่รอตลอดไป

กำหนดเวลาสูงสุดที่จะรอ response — ถ้าเกิน fail fast แทนรอจนระบบค้าง

เปรียบกับ: โทรหาเพื่อน ถ้ารอสาย 30 วินาทีแล้วไม่รับ วางสาย ไม่ใช่รอทั้งวัน — timeout ทำแบบเดียวกัน
ต้องตั้ง timeout ทุก external call — ถ้า downstream service ช้าและไม่มี timeout ทุก request จะค้างรอ thread จะหมด ระบบทั้งหมดพัง
Retry + Exponential Backoff + Jitter

เมื่อ request ล้มเหลว ลองใหม่ — แต่รอนานขึ้นทุกครั้ง + สุ่มเวลาเล็กน้อย

attempt 1: ล้มเหลว → รอ 1s + jitter (0.8-1.2s)
attempt 2: ล้มเหลว → รอ 2s + jitter
attempt 3: ล้มเหลว → รอ 4s + jitter
attempt 4: ล้มเหลว → รอ 8s + jitter
attempt 5: ยังล้มเหลว → return error
ทำไมต้องมี Jitter (สุ่มเวลา)? ถ้าไม่มี jitter และมี client 1,000 ตัว retry พร้อมกันหลัง 2 วินาที server จะโดน 1,000 requests พร้อมกัน = Thundering Herd Problem — jitter กระจาย requests ออกไป
ใช้ retry เฉพาะ transient errors เท่านั้น เช่น network timeout, 503 — ห้าม retry: 400 (ส่งข้อมูลผิด retry ก็ยังผิด), 401, 403, 422
Circuit Breaker — "สะพานไฟ" ป้องกันระบบพัง
เปรียบกับสะพานไฟ (Circuit Breaker) ในบ้าน: ถ้ากระแสไฟเกิน สะพานไฟตัด (open) ป้องกันไฟไหม้ หลังจากระยะเวลาหนึ่งลองต่อใหม่ (half-open) ถ้าปกติก็กลับมาใช้งาน (closed) ได้

Capacity: 10 tokens
Refill rate: 2 tokens/วินาที

10:00:00 — bucket เต็ม (10 tokens)
10:00:00 — ส่ง 5 requests → เหลือ 5 tokens ✓
10:00:01 — เติม 2 tokens → 7 tokens
10:00:01 — ส่ง 10 requests → ใช้ได้ 7 (มีแค่ 7) → 3 ถูก reject ✗

ปัญหาของ REST ในบาง use case

REST ดีสำหรับ public API แต่ใน microservices internal communication มีข้อเสีย:

  • JSON = text format ขนาดใหญ่ serialize/deserialize ช้า
  • HTTP/1.1 = 1 request ต่อ connection (หรือ HTTP/2 ก็ได้ แต่ REST ไม่บังคับ)
  • ไม่มี built-in streaming
  • ไม่มี strict contract — schema drift ได้
เปรียบ REST กับ gRPC: REST เหมือนส่ง SMS (ข้อความ readable แต่ใหญ่) — gRPC เหมือนโทรศัพท์ (binary เร็ว, สองทาง, ตรงกว่า)

gRPC คืออะไร และทำงานยังไง?

gRPC (Google Remote Procedure Call) คือ framework สำหรับเรียก function บน server อีกเครื่อง เหมือนเรียก local function — ใช้ HTTP/2 เป็น transport และ Protocol Buffers เป็น serialization format

HTTP/2 — Transport Layer

  • Multiplexing — หลาย requests พร้อมกันบน 1 connection
  • Binary protocol — ไม่ใช่ text เร็วกว่า
  • Header compression — ลด overhead
  • Server push — server ส่งข้อมูลโดยไม่รอ request

Protocol Buffers — Serialization

  • Binary format เล็กกว่า JSON ~3-10x
  • Parse เร็วกว่า JSON มาก
  • Strongly typed — ผิด type compile error ทันที
  • นิยาม schema ใน .proto file แล้ว auto-generate code

.proto File — สัญญา API ของ gRPC

ก่อนเขียน code ต้องนิยาม interface ใน .proto file — protoc compiler จะ generate code ในภาษาที่ต้องการ (Go, Java, Python, etc.) อัตโนมัติ

syntax = "proto3";          // บังคับ ต้องระบุ version

package student;            // namespace ป้องกัน name collision

option go_package = "./studentpb";  // บอกว่า generated Go code ไปอยู่ที่ไหน

// Service = กำหนด RPC methods (เหมือน interface ใน Java/Go)
service StudentService {
  rpc GetStudent (StudentRequest) returns (StudentResponse);         // Unary
  rpc ListStudents (ListRequest) returns (stream StudentResponse);   // Server streaming
  rpc UploadStudents (stream StudentRequest) returns (Summary);      // Client streaming
  rpc Chat (stream Message) returns (stream Message);               // Bidirectional
}

// Message = struct ของ data
message StudentRequest {
  int32 id = 1;              // = 1 คือ field number (ไม่ใช่ value!)
  optional string name = 2;  // optional field
}

message StudentResponse {
  int32 id = 1;
  string name = 2;
  string major = 3;
  string email = 4;
  // ถ้าเพิ่ม field ใหม่ ต้องใช้ field number ต่อไป (5, 6, ...)
  // ห้ามเปลี่ยน field number ที่มีอยู่! = breaking change
}
Field Numbers — สำคัญมาก! Protobuf ใช้ field number ใน binary encoding ไม่ใช่ field name — ถ้าเปลี่ยน id = 1 เป็น id = 5 client เดิมจะอ่าน data ผิด แต่เปลี่ยนชื่อ field ได้ (backward compatible)

Prometheus Metrics — วัด performance ของ API

ทุก request จะถูกนับและวัด latency อัตโนมัติ ผ่าน middleware

// Counter — นับจำนวน requests ทั้งหมด แยกตาม method/path/status
var httpRequestsTotal = prometheus.NewCounterVec(
    prometheus.CounterOpts{
        Name: "http_requests_total",
        Help: "Total number of HTTP requests",
    },
    []string{"method", "path", "status"},
)

// Histogram — กระจาย latency (เช่น p50, p95, p99)
var httpRequestDuration = prometheus.NewHistogramVec(
    prometheus.HistogramOpts{
        Name:    "http_request_duration_seconds",
        Buckets: prometheus.DefBuckets,   // [.005, .01, .025, .05, .1, .25, .5, 1, 2.5, 5, 10]
    },
    []string{"method", "path"},
)

// Middleware ที่บันทึก metrics ทุก request
func prometheusMiddleware() gin.HandlerFunc {
    return func(c *gin.Context) {
        start := time.Now()
        c.Next()    // เรียก handler จริง
        duration := time.Since(start).Seconds()
        status := fmt.Sprintf("%d", c.Writer.Status())
        // บันทึก metrics หลัง handler ทำงานเสร็จ
        httpRequestsTotal.WithLabelValues(c.Request.Method, c.FullPath(), status).Inc()
        httpRequestDuration.WithLabelValues(c.Request.Method, c.FullPath()).Observe(duration)
    }
}

Graceful Shutdown — ปิดอย่างสุภาพ

Kubernetes ส่ง SIGTERM ก่อน kill container — เราต้องรับ signal แล้วรอให้ in-flight requests เสร็จก่อน

// Start server ใน goroutine (non-blocking)
go func() {
    if err := srv.ListenAndServe(); err != nil && err != http.ErrServerClosed {
        log.Fatalf("Server error: %v", err)
    }
}()

// Block รอ signal จาก OS หรือ Kubernetes
quit := make(chan os.Signal, 1)
signal.Notify(quit, syscall.SIGINT, syscall.SIGTERM)
<-quit    // หยุดตรงนี้จนกว่าจะได้รับ signal

log.Println("Shutdown signal received – draining connections...")

// Graceful shutdown: รอ max 15 วินาที
ctx, cancel := context.WithTimeout(context.Background(), 15*time.Second)
defer cancel()
srv.Shutdown(ctx)    // รอ requests ที่กำลัง process อยู่ให้เสร็จก่อน
ถ้าไม่มี Graceful Shutdown: K8s kill process ทันที — requests ที่กำลังทำงานอยู่จะขาดกลางคัน ทำให้ data inconsistent หรือ user ได้รับ error กะทันหัน

package main

import (
    "context"
    "log"
    "net"
    pb "grpc-student/studentpb"   // import generated code
    "google.golang.org/grpc"
)

// server struct ต้อง embed UnimplementedStudentServiceServer
// ถ้า .proto เพิ่ม method ใหม่ แต่เรายังไม่ implement → ไม่ compile error
type server struct {
    pb.UnimplementedStudentServiceServer
}

// Implement GetStudent — signature ต้องตรงกับ .proto
func (s *server) GetStudent(ctx context.Context, req *pb.StudentRequest) (*pb.StudentResponse, error) {
    log.Printf("Received: GetStudent id=%d", req.Id)

    // ในโลกจริงจะ query database แต่ lab ใช้ mock
    return &pb.StudentResponse{
        Id:    req.Id,
        Name:  "Alice Johnson",
        Major: "Computer Science",
        Email: "alice@university.com",
    }, nil
}

func main() {
    // เปิด TCP port 50051 (gRPC convention)
    lis, err := net.Listen("tcp", ":50051")
    if err != nil {
        log.Fatalf("Failed to listen: %v", err)
    }
    grpcServer := grpc.NewServer()
    pb.RegisterStudentServiceServer(grpcServer, &server{})  // register implementation
    log.Println("gRPC Server :50051")
    grpcServer.Serve(lis)  // blocking
}

Step 6: client/client.go — เรียก server

package main

import (
    "context"
    "log"
    "time"
    pb "grpc-student/studentpb"
    "google.golang.org/grpc"
)

func main() {
    // เชื่อมต่อ gRPC server
    // grpc.WithInsecure() = ไม่ใช้ TLS (dev/lab เท่านั้น — production ต้องใช้ TLS)
    conn, err := grpc.Dial("localhost:50051", grpc.WithInsecure())
    if err != nil {
        log.Fatalf("Could not connect: %v", err)
    }
    defer conn.Close()

    // สร้าง client stub — auto-generated โดย protoc
    // stub ทำให้เรียก remote method เหมือน local function
    client := pb.NewStudentServiceClient(conn)

    // Context with timeout — ถ้า server ไม่ตอบใน 1 วินาที → cancel
    ctx, cancel := context.WithTimeout(context.Background(), time.Second)
    defer cancel()

    // เรียก RPC — เหมือนเรียก local function ธรรมดา
    res, err := client.GetStudent(ctx, &pb.StudentRequest{Id: 101})
    if err != nil {
        log.Fatalf("Error: %v", err)
    }
    log.Printf("ID: %d, Name: %s, Major: %s", res.Id, res.Name, res.Major)
}
